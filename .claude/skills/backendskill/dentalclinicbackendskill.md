# Dental Clinic Backend (Flask)

## What this codebase is

A Flask marketing site + appointment booking system + JSON REST API for a dental clinic, built with the **application factory + Blueprints** pattern. SQLAlchemy ORM (SQLite in dev, Postgres in prod via `psycopg3`), Flask-Migrate/Alembic for schema changes, Flask-WTF for CSRF-protected forms, Flask-RESTX for the versioned JSON API (`/api/v1`, Swagger at `/api/v1/docs`), Flask-Mail for background-thread email, Jinja2 + Tailwind (CDN, no Node build step).

Read `references/conventions.md` before scaffolding anything — it has the exact file-by-file template to follow for each kind of addition. The patterns below are load-bearing: this app has ~8 existing blueprints that all follow them identically, so deviating creates inconsistency the next contributor (human or Claude) will trip over.

## Core architectural rules (always apply)

1. **Every feature area is its own blueprint package** at `app/<name>/` with an `__init__.py` defining the `Blueprint` object and a `routes.py` imported at the bottom of `__init__.py` via `from app.<name> import routes  # noqa: E402,F401` — this avoids circular imports. Register the new blueprint in `register_blueprints()` in `app/__init__.py`.
2. **All models live in `app/models.py`**, inherit `TimestampMixin` for `created_at`, and use a unique indexed `slug` column (not the numeric id) as the public identifier for any content that gets its own detail page. Any change here requires a new Alembic migration: `flask db migrate -m "..."` then `flask db upgrade`.
3. **The REST API is separate from the HTML blueprints.** New API resources go in `app/api/<resource>.py` as a Flask-RESTX `Namespace`, registered in `app/api/__init__.py`. The whole `api_bp` is CSRF-exempt (stateless JSON) — every other blueprint keeps global CSRF protection, so never exempt an HTML-facing blueprint.
4. **Forms are Flask-WTF classes in `app/forms.py`**, not scattered across blueprint files. `SelectField` choices that depend on DB state are populated in the route handler at request time (see `_populate_choices` pattern), never hardcoded on the class.
5. **No repository/service layer.** Route handlers call `db.session.add()` / `db.session.commit()` directly. Keep it that way for consistency rather than introducing a new abstraction layer for one feature.
6. **No raw SQL** — everything goes through the SQLAlchemy ORM.
7. **Secrets and environment-specific values go in `.env`**, loaded via `python-dotenv` in `run.py`, never hardcoded. If a new feature needs a new setting (an API key, a notification address, etc.), add it to `.env.example` with a safe placeholder and read it via `app.config` (wired in `config.py`), not `os.environ` directly in route code.
8. **Email is fire-and-forget.** If a new feature should notify someone, follow `app/utils/email.py`'s background-thread dispatch pattern rather than sending synchronously in the request handler.

## Workflow for adding a new feature

1. Confirm what kind of addition it is: a new HTML page/section (blueprint), a new data type (model), a new API resource, or a new form — often it's a combination (e.g. "add insurance providers" = model + blueprint + maybe API resource).
2. Open `references/conventions.md` and copy the relevant template(s) — don't write these from scratch, the existing code already has the exact shape to match.
3. Wire it in: register new blueprints in `app/__init__.py`, register new API namespaces in `app/api/__init__.py`, add new models to `app/models.py` and generate a migration.
4. If the feature touches the database, remind the user to run `flask db migrate -m "<description>"` then `flask db upgrade` — don't run these yourself unless asked, since migration messages should describe the actual change and the user may want to review the autogenerated migration first.
5. Match the existing template/static-file conventions (Jinja2 extending `base.html`, Tailwind utility classes, no new build tooling) if the feature includes user-facing pages.

## Guardrails

- Never read or print the contents of `.env` — it holds real per-environment secrets. Only `.env.example` (with placeholder values) should ever be edited or shown.
- Don't introduce a new database, ORM, templating engine, or JS build step "to do it properly" — the whole point of this app is zero-build-step simplicity. If a request would require that, flag the tradeoff to the user rather than silently expanding scope.
- This app has no automated test suite (per `CLAUDE.md`); verify manually the way the project already does — e.g. hitting the route/API endpoint and checking terminal logs — rather than assuming a `pytest` setup exists.
